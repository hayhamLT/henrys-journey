## The problem this fixes

Today every world is a generic puzzle gimmick with a money **label** (keys = "needs before wants", bombs = "managing risk"). A smart kid learns *"this is a routing puzzle,"* not *"this is how money works."* The skeptic pass proved it: in **all 10 worlds**, a child could win while ignoring the money concept entirely.

**The governing rule for every verb below:** *a kid cannot win optimally without enacting the lesson.* The mechanic IS the lesson, not a sticker on it.

## The five ground-truth engine facts (verified against live code)

1. **The solver is reachability-only.** `solve()` does BFS over `(pos, collectedMask, crumbledMask)` and returns the shortest goal-reaching path. It has **zero** score/timing model and the generator validates all 80 candidates through it (never through `simulateGame`). → **Never make the in-puzzle solver score-aware.** Instead either (a) make the lesson a *counter-gated reachability fact* by adding a small **bounded** dimension to the BFS state (wallet/reserve/bankBucket), or (b) keep `solve()` reachability-only and do value/timing checks at **gen time** by simulating the solved path through the new value function.
2. **Per-step value is a small addition, not a rewrite.** The combo chain already mutates per-step state on the live index `i`. One shared *Live Coin Accounting* hook (~15–30 lines) powers drain, growth, inflation, and compounding — built once, reused four times.
3. **Nothing the design calls "reuse" exists yet.** There is no run-wallet, reserve, per-step value, or new objective field. `Wallet.tsx` is the persistent *meta* wallet, not an in-level HUD. So W4, W5, W6, W7, W8, W9 are all genuinely `needsNewEngineCapability: true`. Every new `Level` field must also land in `LevelDataForShare` or shared/daily/custom levels silently lose the mechanic.
4. **`measureDifficulty` is purely structural** and blind to every value/timing/spend mechanic → each such world needs an explicit hand-tuned weight term or the monotonic DIFF band breaks.
5. **The medal rule contradicts slow-is-optimal worlds.** Gold requires `underPar && timeBonus>0` — directly opposed to W5 "wait to ripen" and W9 "bank early." Those worlds need a medal exemption.

## Cross-world arc (the ladder)

**Rung 1 — money is a thing you gather** (W0 earn → W1 spend-in-priority-order).
**Rung 2 — money means choosing** (W2 compare → W3 inspect-the-scam).
**Rung 3 — money behaves over time**, all on one shared per-step counter (W4 drain → W5 grow → W6 inflate-vs-goal). *The conceptual heart.*
**Rung 4 — money is managed** (W7 allocate → W8 reserve).
**Rung 5 — mastery** (W9 integrate, with early-bank compounding as the one new integrating twist).

Verb count rises by exactly one per world; difficulty rises monotonically because each verb adds a genuinely new *planning dimension*, never just bigger numbers.

## Shared engine work (build once, reuse)

- **CAP-1 Live Coin Accounting** — one shared per-step value hook in `simulateGame`'s step loop (collect site + teleport-dest site), reading live index `i`. Powers W4 drain, W5 growth, W6 inflation, W9 banked growth. ~15–30 lines, integer/quantized/capped.
- **CAP-2 Run wallet + bounded solver dimension** — per-run `wallet` (and W8 `reserve`) seeded from new `Level` fields. **The load-bearing part is the solver:** add `wallet`/`reserve` as *bounded* (0–5) dims to `QueueState` + `getVisitedKey`, model wallet-mutating tiles in the BFS transition, and add affordability tests at the goal check (`solver.ts:141`) and in `isMoveValid`. Without these the 80-candidate loop ships unwinnable/trivial levels. Used by W1, W4, W7, W8.
- **CAP-3 New cell types / flags** — `WantTile` (PINK), `Package_Savings` (GREEN grow), `Inflating_Coin` (two-tier), `Toll_Gate` (priced ForceField variant), `Shock`/`Liquid_Cash`/`Illiquid_Vault`. W3 disguise = planning-layer flags (`disguised: string[]` + `inspectBudget`), **not** new enum values. Reuse retired Vault/GoldBarStack art as GREEN growth + GOLD-locked illiquid vault.
- **CAP-4 New objective types + win-gate fields** — `min_grow_score` (W5), vault-growth gate (W9), per-level flags `startWallet`/`gatePrice`/`startingPurse`/`purseFloor`/`suppressEfficiencyBonus`, and `FailureType 'broke'`.
- **CAP-5 Serialization + difficulty parity** — every new `Level` field must also be added to `LevelDataForShare` (`types.ts:173`) **and** weighted in `measureDifficulty` (`levelGenerator.ts:102`).
- **CAP-6 Gen-time verification harness** — for value/timing worlds (W2/W5/W6/W9), after the existing reachability solve, simulate the solved path through the new value function and assert it clears the floor; for wallet/reserve worlds (W7/W8) verify a solvent solution exists and that no route funds everything. Graceful fallback to a simpler composition when a candidate fails (critical for W9).
- **CAP-7 In-level coin/resource HUD + planning-phase preview** — a NEW lightweight HUD (not `Wallet.tsx`) showing coins-this-trip, the run wallet projected **live during planning** (the sim only runs on RUN today, so a plan-phase preview is required), draining purse, swelling savings, goal meter + greying coins, reserve meter. Visually distinct from end-of-level SCORE so a 7yo never conflates coins with points.

## Build order

- **Phase 0 — Shared spine** (W0): cheapest real change (relax W0 gate + the in-level coin HUD); stand up CAP-5 plumbing (`FailureType 'broke'`, wire `measureDifficulty` + `LevelDataForShare` to accept new fields). De-risks HUD + serialization before any solver work.
- **Phase 1 — Run wallet + bounded solver dim** (W1): the keystone (CAP-2 + WantTile). Getting the three-part solver fix right once pays off in W2/W4/W7/W8.
- **Phase 2 — Comparison + scams** (W2, W3): no new sim state; planning-UI heavy. W2 = twin-route gen verification + `scoreObjective` gate lift to world 2 (needs monotonic review). W3 = planning-layer disguise + second gen-time solve.
- **Phase 3 — Live Coin Accounting** (W4, W5, W6): build CAP-1 once, then drain → grow → inflate. The conceptual core and highest design risk.
- **Phase 4 — Management** (W7, W8): extend the bounded-wallet solver state. W7 toll-gates; W8 second counter + shocks (depends on W4 crumble, W5 vault).
- **Phase 5 — Mastery capstone** (W9): composes everything + the bank-growth win-gate; curated 3–4 mechanics/level with CAP-6 fallback.

## Open questions (need a human decision before/at build)

1. **Gate lifts vs monotonic difficulty** — W2 needs `scoreObjective` lifted from world 6 → 2; W0 uses `collect_ratio` as a relaxed gate. Both change `worldGate` and the DIFF bands. OK to re-review the monotonic curve after?
2. **Medal-rule exemption** — (a) exempt grow/vault levels so Gold = hit the growth target (touches `computeMedal`), or (b) set par to the growth-optimal length (keeps medals untouched, inflates par). Pick one, apply to W5 + W9. *Recommend (a).*
3. **Solver state budget** — caps proposed (wallet 0–5, reserve 0–5, tolls 3–4, prices 3–8). Confirm acceptable generation time for the 80-candidate loop on boss grids, or lower candidate count / grid size for W7–W9.
4. **W3 inspect depth** — cheap (plan-commit guard + gen-time second solve, sim/solver untouched) vs cleaner (solver flag run twice). Which for v1?
5. **Serialization scope** — do community/builder/daily levels support the new verbs in v1, or are the new verbs **campaign-only** at first (defers serializer/builder work, ships campaign sooner)?
6. **W6 vs W5 distinction for 7–11s** — inflation and compounding are inverse forces and risk feeling identical. Validate via playtest, or lead W6 with the goal meter alone for more levels before erosion turns on?
7. **Temptation placement (W1/W4/W6)** — build a dedicated "want must shave ≥2 moves" placement heuristic, or is manual review of generated samples enough for v1?
